# 人物牵挂与追读体验改进分析

日期：2026-10-13。范围：`remote-src` 的概念、蓝图、章纲、章节导演、正文、评审与写作台。

用户明确的主要问题是：**剧情有事件，但不关心人物，也不想追读。**

本报告依据实际代码与提示词检查。尚未用本次用户的具体生成正文做对照，因此下面区分确定的链路缺口与由此推断的阅读风险；不把静态审计当成已经证明的生成质量结论。

## 1. 判断

系统已有情感核心、读者承诺、场景选择与后果、人物意义记忆、情感审校、口吻试写及连续章节盲读。最值得改的是这些能力在规划、生成、采用、下一章之间的衔接。

目前存在一种结构性风险：规划先安排发生的事件，正文阶段再收到人物情感提醒。模型于是能完成事件、补上情绪表达，却未必让事件来自这个人物独有的欲望、矛盾和关系。阅读体验容易成为“知道发生了什么，但不在乎结果”。

目标应是：**读者认识一个有具体牵挂的人 → 看见他在阻力下作选择 → 经历选择的代价和关系变化 → 想知道这些后果会怎样继续。**

这也适用于日常、余波和关系章，不要求每章增加危险、眼泪、反转或心理独白。

## 2. 代码证据与影响

### 2.1 情感核心进入正文，但没有稳定进入章纲与审稿

已有能力：`ConceptDossier.emotional_core` 包含最舍不得、会为谁破例、核心关系、两难选择、情感承诺；确认页已有“读者会在乎什么”。正文组装和逐场生成也直接注入情感核心。

确定缺口：

- 初始蓝图的设定段收到立项书，但章纲段使用 `_build_settings_summary()`；其中角色只保留姓名、身份、目标，没有明确传递人物缺陷、关系及立项书情感核心。
- `regenerate-outlines` 的精简蓝图白名单不含角色与关系。需要区别：直接 `/chapters/outline` 的单区间路径仍传完整蓝图，并非所有续纲路径都删角色；但也未直接注入项目的立项书情感核心。
- 蓝图审稿的 `slim_settings` 不含角色与关系，立项书只单独提取 `anticipation`。七维量表已有开局、兑现、钩子、升级等，但没有独立验收人物牵挂是否被安排成具体选择。

人物信息仍可能通过梗概、章纲摘要间接进入，不能说完全丢失；问题是缺少可靠的直接传递和验收。

### 2.2 导演规划人物选择时，人物资料不足

完整导演的蓝图硬约束摘要主要保留题材、基调、文风、世界规则及角色名字；`generate_chapter_mission()` 的输入没有直接携带角色欲望、缺陷、关系和情感核心。轻量导演同样主要收到前章摘要、结尾、本章大纲及写作指令。

逐场路径已有 `choice`、`consequence`、`emotion_before/after`，但补齐场景契约的输入仅有 mission、scenes、chapter_goals、previous_tail。情感核心、人物意义记忆在后面的正文生成阶段才单独注入。候选节拍搜索要求保持既定人物选择与终态，也不能自由弥补前面选得不好的剧情。

风险：人物选择主要用来完成场景任务，而不是由其独特动机产生；最终“正确完成契约”也未必“读者愿意陪他走下去”。

### 2.3 续纲规划存在存储契约不一致

`extract_outline_planning_metadata()` 返回的是规划字典本身；普通章纲生成和重排调用将其直接用作 metadata。`NovelService.update_or_create_outline()` 只在存在 `metadata.planning` 时同步章节蓝图表，下游导演读取该表；节奏注入也读取 `metadata.planning`。

因此在这些路径中，新规划字段可能已保存到 metadata 顶层，却没有同步到导演使用的章节蓝图。已有表记录时还可能继续使用旧规划。初始蓝图路径正确包装了 `planning`，滚动定向修订也有包装，不能概括为全系统规划都失效。

先统一写入格式、兼容读取历史顶层字段，并验证初始蓝图、直接续纲、后台续纲、重排四条入口。否则新增人物字段可能再次出现“界面有、生成没用”的问题。

### 2.4 情感连续性和追读控制随路径切换

人物意义记忆已有信念、代价、关系、没说破的事、心结承诺，且绑定采用版本与正文 hash。但其开关默认关闭，默认生效依赖 premium 与后台质量配置。读者候选节拍控制仅在 premium 场景路径启用。

另外，`enable_polish=True` 会使 premium 默认走整章后处理路径，除非显式请求场景模式。选择更精修的配置可能绕开原有场景决策和读者候选控制。不能据此断言精修一定更差，但用户应能理解功能之间的实际影响。

建议将“保存并继承人物变化”设为基础写作数据；用候选数量、检查深度与精修预算区分模式。基础记忆可合并到已有采用后抽取，避免每章额外叠加完整评审。

### 2.5 有诊断能力，但反馈与质量展示仍有缺口

写作台已有情感审校引用、保护原句和局部修改对照，值得复用。后台读者模拟也产出继续阅读意愿与弃书风险，但当前前端未找到消费这些字段的代码。

规划画布和章级规划类型主要围绕章节功能、爽点、钩子、伏笔与禁写，没有明确展示本章人物牵挂、选择代价与关系前后变化。

作品概览在没有评审数据时，用字数均匀度估“节奏”、完成率估“张力”、平均字数估“人物”、章数估“世界观”。这些统计不能说明人物是否值得关心，建议无评审就显示“尚未评估”，把完成度单独展示。

### 2.6 部分运行时指令仍套统一节奏，与现有情感原则冲突

章纲提示词已允许安静关系推进和局部兑现，但续纲运行代码仍要求批次末以新悬念或新冲突结束。技术批次会因此被当作故事节拍，人物余波可能被迫再次转向事件接力。

综合优化启用时还要求“30% 铺垫 / 40% 兑现 / 30% 微反转”，并同时要求不改变情节和关系。对日常、告别、余波等章节，这种统一配方既可能不适用，也给改写制造相互冲突的目标。该风险只适用于实际启用综合优化的路径，不能概括为所有正文都会这样改。

应将运行时追加指令、主提示词和优化器统一为按章节功能评价；局部闭环后的情感余韵也能延续阅读期待。

## 3. 功能如何改

### 3.1 蓝图同时规划外在事件与人物关系

直接复用立项书已有的情感核心，补齐本书主要人物与关系的行动逻辑：人物想得到什么、为什么偏偏他在乎、最怕失去什么、哪条原则会使他做出有代价的选择、核心关系双方各自想要什么。

卷级规划同时写清“外在目标达成什么”与“这个过程中人物或关系发生什么不可轻易撤回的变化”。重要事件应能解释为什么由这个人物作出这个行动；若换个名字就可以原样完成，要检查人物是否只承担剧情功能。

不把这些做成更多必填问卷。系统根据已有讨论提出具体情境和推荐，作者只改关键分歧；没有依据的情感设定保持开放。

### 3.2 每章生成一张简短的“人物与阅读期待”卡

先在章级 planning 中增加一个可选、兼容旧稿的结构块，优先覆盖：

| 内容 | 要回答的问题 |
| --- | --- |
| 当下牵挂 | 这章他想得到或保住什么，读者为何在乎？ |
| 关键行动或选择 | 哪个行为来自这个人的动机，而非大纲需要？ |
| 代价与后果 | 做了以后失去什么，或必须面对什么？ |
| 关系变化 | 对谁的信任、亏欠、误解或依赖发生怎样的变化？ |
| 后续期待 | 读者下一章想看到什么后果或关系进展？ |

不是每章都要重大抉择或五项齐全。日常章的一次回避、照顾、拒绝、默契也可以成立；字段没有实际意义时留空。

这张卡应进入初始排章、续纲、蓝图审稿、章节导演、场景契约和正文。只传本章相关人物及关系的压缩卡，控制输入量；不把全书档案反复完整堆入提示词。

### 3.3 在长篇详细排章前验证“读者是否在乎”

现有 `StoryVoiceTrial` 是同剧情不同口吻，适合选表达，但不能验证关键选择本身是否有吸引力。保留它，增加“开篇试读”或“关键人物场景试读”。

先读一个能认识人物的场景，再读一个暴露其选择与关系后果的场景。反馈只问：在乎谁、为什么在乎、想知道接下来什么；找不到答案时回到人物/场景规划修订。

全书保留方向与卷级承诺，远期章纲可先粗排，近 3–5 章详细规划。复用已有滚动修订，在采用正文后同时检查事件推进、关系记忆和未兑现期待。3–5 章是建议起点，应按实际题材和成本调整。

### 3.4 区分表达不足与剧情选择不足

“情绪转折没有触发”“对白太直白”可以用现有证据化局部编辑解决。

“人物没有真正选择”“付出什么都不重要”“配角只负责帮主角过关”属于场景或章纲问题，应该回到规划层提供两个有差异、遵守既定故事事实的修法，再生成一个待采用版本。不要期待只改几句心理描写能解决人物不值得关心。

已有局部编辑和改写护栏很好地保护事实、潜台词及原句。需要一个显式的剧情修订入口，定义允许变化的场景目标与范围，避免把这种修订混入普通润色，也避免无边界重写全章。

### 3.5 让评审成为可执行的阅读反馈

沿用 `EmotionalReviewPanel`，将反馈聚焦到：人物的得失为何没有重量、哪个选择缺少依据、哪个转折被一句叙述跳过、哪段对白抹平了关系、读者期待在哪里中断。

每条反馈引用正文，提供“修改这个场景”的入口；已有 strengths/protected_passages 继续保留。后台读者模拟可显示为 AI 试读意见，不包装成真实读者留存率。正文变化后旧结论必须标记失效。

用户自己的“这里不在乎人物”“更想看两人怎么相处”也应能定位段落并进入本章修订及后续规划，而不只作为一次性聊天。

## 4. 优先级与最小交付

| 优先级 | 交付 | 验收 |
| --- | --- | --- |
| P0 | 统一 planning 存储契约，补齐规划阶段人物/情感输入 | 四条章纲入口都能把规划传到导演；新旧字段不丢、不混用旧计划 |
| P0 | 清理批次末强制新冲突及统一爽点比例 | 余波、关系、日常章按本章功能生成和修改 |
| P0 | 停止用字数和完成率冒充人物、张力质量分 | 没有评审显示未评估；生成更多章不自动提高人物质量 |
| P1 | 人物与阅读期待卡进入排章、导演和审稿，写作台可确认 | 重要选择有具体动机、代价及关系后果；允许安静章 |
| P1 | 采用后保留人物意义和关系变化，后续相关场景检索 | 前章变化在后续言行中留下证据；改选版本后旧记忆失效 |
| P1 | 试读与针对场景的剧情修订 | 读者反馈能回到计划，且修法有差异、可预览、可撤回 |
| P2 | 连通后台试读诊断与用户段落反馈 | 可定位、可修订、失败可见、旧稿结论不复用 |

建议首轮只做“P0 + 规划卡贯通 + 一组连续章节对照”。先确定这条改动能改善人物牵挂，再扩大到更多自动修订与界面功能。

## 5. 怎样判断真的改好了

直接复用现有连续章节盲读模块，不另造一套只有总分的评价体系。它已经支持 3–8 个连续章节，比较人物牵挂、关系记忆、节奏、兑现及潜台词，并要求跨章逐字引用；还有真人试读票与继续阅读问题。

证据：[连续章节评价维度](D:/Ubuntu/home/aikev/code/arboris-novel/remote-src/backend/app/services/bench/serial_reading.py:12)、[真人试读票](D:/Ubuntu/home/aikev/code/arboris-novel/remote-src/backend/app/services/bench/serial_reading.py:92)、[证据验证](D:/Ubuntu/home/aikev/code/arboris-novel/remote-src/backend/app/services/bench/serial_reading.py:116)。

比较同一立项、共同前情、相同模型配置与相近预算下的旧链路和新链路，读 3–5 个连续章节，隐藏来源与 AI 推荐，交换版本顺序。记录：

1. 更愿意继续读哪版，或两版都不愿意；不要强迫二选一。
2. 最在乎谁，以及哪句行动/对白使其值得在乎。
3. 下一章具体期待什么；这个期待是否来自本书已建立的人物和关系。
4. 前章关系变化在后章有没有留下行为证据，代价有没有被立刻抹去。
5. 从哪一段开始失去兴趣，修订有没有解决该位置的问题。

AI 评审用于定位和辅助比较，真人继续阅读意愿单独记录。没有真实结果前，不宣称提升留存率。剧情一致性、成本和延迟也同时记录，防止用更多调用掩盖改进成本。首次实施需要补数据契约回归；主观阅读质量则通过上述连续正文对照验证。

## 6. 一个改造示例

事件型章纲：主角去黑市买药，遭到截杀，反杀后发现幕后组织。

人物驱动的章纲：主角攒够了给师父治病的钱，师父却拒绝来路不明的药。他在黑市发现救命药与师父当年留下的信物有关，必须决定是否打破对师父的承诺。逃出追杀后，他保住了药，却选择隐瞒来源；师父认出包装，仍没有拆穿。

这里值得追的可以同时是“药背后是什么”与“这段彼此知道却不说破的关系将怎样变化”。事件数量不是重点；人物的珍惜、选择和后果让事件有重量。这只是说明机制的例子，不是给所有题材套师徒、疾病或秘密模板。
