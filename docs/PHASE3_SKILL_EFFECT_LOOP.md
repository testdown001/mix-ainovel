# 第三阶段：技能效果闭环与项目化

## 目标

把第二阶段的“可发布技能版本”继续接到真实创作结果上：作者能看到技能对章节质量的影响，能只为当前小说定制规则，验证器能把命中位置和原因反馈给作者。

## 本阶段交付

### 1. 质量评分回写

- 每次章节生成会记录本次实际解析到的技能版本 ID。
- 章节完成后的验证报告会计算 0–100 的质量分：通过项、人工关注项、失败项和待执行项分别计入权重。
- 评分、状态分布和验证摘要回写到同一批 `writing_skill_usages`，不会污染其他章节或其他版本的指标。
- 回写失败只影响指标，不会让已经成功的正文变成失败。

### 2. 当前小说专属技能副本

- 作者可从系统技能创建“本书专属副本”，副本只在当前小说可见、可用。
- 副本保留 `base_skill_id` 和 `base_version_id`，编辑时能看到系统基线与本书规则的数量差异。
- 副本首次创建即发布；后续编辑仍采用草稿 → 人工发布的不可变版本流程。
- 其他小说和其他作者不能解析或使用该副本。

### 3. 检查器命中证据

- `checker_keys` 通过安全白名单映射到确定性的检查器，不执行数据库中的任意代码。
- 当前接入视角越界、比喻密度、修饰堆叠、自然收束和全知旁白检查。
- 每条提示携带 `char_start`、`char_end`、摘录、原因和严重级别，方便写作台跳转定位。
- 检查器结果进入章节验证报告，并可用于后续质量趋势分析。

## API 与数据迁移

- `POST /api/skills/{skill_id}/project-copy`
- `writing_skills.base_skill_id/base_version_id`
- 迁移版本：`k5f6g7h8i9j0`

## 验收标准

- 生成完成后能按版本查到质量回执和验证摘要。
- 项目副本在目录中可见，系统基线仍保持只读；修改副本不会改变其他项目。
- 命中规则时报告至少包含一条有效文本范围证据；无命中时明确返回通过。
- 草稿版本不会被生成链路解析，项目副本权限校验通过。
