## 一、当前架构分析与瓶颈诊断

### 1.1 技术栈现状

| 层级 | 技术 | 状态 |
|------|------|------|
| **后端框架** | FastAPI (Python 3.11) + Uvicorn | 单进程，异步但未充分利用 |
| **数据库** | MySQL 8.0+ / SQLite + libsql(向量) | 默认连接池，无读写分离 |
| **缓存** | Redis（已配置未充分使用） | 仅 Mem0 长期记忆用 |
| **任务调度** | 无 | HTTP 请求周期内同步完成 |
| **部署** | Docker Compose 单容器 | 无负载均衡，无水平扩展 |
| **前端** | Vue 3 + TypeScript + Naive UI | SSE 流式，无 WebSocket |
| **Agent 系统** | 三省六部多 Agent（Python） | 消息总线内存级，无持久化 |

### 1.2 核心瓶颈（按严重程度排序）

#### P0 - 致命瓶颈

| # | 瓶颈 | 位置 | 影响 |
|---|------|------|------|
| 1 | **无任务队列** | `writer.py` 路由 | 所有章节生成在 HTTP 请求周期内完成，30-120s 阻塞 worker |
| 2 | **单容器部署** | `docker-compose.yml` | 单点故障，无法水平扩展 |
| 3 | **LLM 调用无并发控制** | `llm_service.py` | 无限流/令牌桶，突发流量直接打爆 LLM API |
| 4 | **无多租户隔离** | 全局 | 用户间数据无隔离，无权限分级 |

#### P1 - 严重瓶颈

| # | 瓶颈 | 位置 | 影响 |
|---|------|------|------|
| 5 | **数据库连接池不足** | `db/session.py` | 默认连接池，高并发时连接耗尽 |
| 6 | **Agent 消息总线内存级** | `message_bus.py` | 无持久化，进程重启丢失所有状态 |
| 7 | **无缓存层** | 全局 | 蓝图/角色/提示词每次查库 |
| 8 | **向量库单文件 libsql** | `vector_store_service.py` | 无法支撑多用户大规模 RAG |

### 1.3 千人并发承载力评估

**假设条件**:
- 千人同时在线，峰值 100 人同时触发章节生成
- 单章节生成耗时 60s（含 LLM 调用 + 后处理）
- 单 Uvicorn worker 有效并发: 20-30 请求（I/O-bound 场景）

```
当前架构吞吐量 ≈ 30 并发请求 / 60s = 0.5 章节/秒 = 30 章节/分钟
100 人同时生成排队时间 = 100 / 0.5 = 200 秒 (3.3 分钟)
1000 人同时生成排队时间 = 1000 / 0.5 = 2000 秒 (33 分钟)
```

**结论**: 当前架构无法支持千人并发，甚至百人同时生成就会导致严重排队。

#### Go vs Python 对比

| 维度 | Python | Go | 对 Arboris 的影响 |
|------|--------|-----|-------------------|
| **LLM 框架生态** | 极其丰富（LangChain、LlamaIndex、CrewAI...） | 快速追赶（Eino、LangChainGo、ADK Go） | Go 生态可用但选择少 |
| **HTTP 吞吐量** | 基准 1x | 40-50x | 网关层优势明显 |
| **内存占用** | 高（GC 暂停明显） | 中（并发 GC 优化） | 降低 60% 服务器成本 |
| **并发模型** | asyncio（协程） | goroutine（轻量级线程） | goroutine 更高效，百万级并发 |
| **LLM Gateway 延迟** | +5,789ms 开销 | +1.7ms 开销 | 关键路径差距 3400x |
| **开发效率** | 高（动态类型、丰富生态） | 中（静态类型、生态较小） | Python 原型更快 |
| **AI 工具链** | PyTorch/TF/HuggingFace 原生 | 需 FFI 或 API 调用 | AI 推理层 Python 不可替代 |
| **运维复杂度** | 依赖管理复杂 | 单二进制部署 | Go 运维更简单 |

#### 关键结论

**Go 在 AI 应用的定位已经明确：基础设施层（Gateway、队列、路由）而非 AI 逻辑层。**

- Go 官方博客明确表示：LLM 应用需要 REST/RPC、并发和性能——这正是 Go 的优势领域
- 字节跳动 Eino 框架证明了 Go 做 LLM 应用的可行性，但其核心价值仍在**编排和调度**，而非模型推理
- Bifrost（Go 实现的 LLM Gateway）比 Python 版快 40-50 倍，但其优化的是**路由和连接管理**，不是 AI 逻辑

### 2.3 任务队列选型对比

| 特性 | **Celery** (Python) | **Temporal** (Polyglot) | **Asynq** (Go) |
|------|---------------------|------------------------|-----------------|
| 语言 | Python | Go/Java/Python/TS | Go |
| Broker | Redis/RabbitMQ | 内置持久化引擎 | Redis |
| 最佳场景 | 批量推理、简单 ML 任务 | 复杂多步 AI 工作流、Agent 编排 | 高吞吐后台任务 |
| 状态管理 | 最小 | 完整持久化执行 | 基础（Redis） |
| 搭建复杂度 | 低 | 高（需 Temporal Server） | 低 |
| 长运行工作流 | 有限 | 优秀（支持天/周级） | 有限 |
| 即发即忘 | 优秀 | 过度设计 | 优秀 |
| 监控 | Flower | 内置 Web UI | AsynqMon + Prometheus |
| 吞吐（2026 基准） | 10K tasks/s（16 worker） | 依赖后端，中等 | 极高，Go 原生性能 |

**选型建议**:
- **短期（Python 阶段）**：Celery + Redis，成熟可靠，与现有代码无缝集成
- **Go 阶段**：Asynq，轻量高效，Redis 生态复用
- **如需复杂工作流编排**：Temporal，但运维成本高，建议在规模真正需要时再引入

### 2.4 LLM API 并发控制最佳实践

2026 年业界共识：**Token-aware 限流取代传统 RPS 限流**。

```
限流层级（由严到宽）:
  Request Level → max_tokens 硬限制
    → User Level → TPM (Tokens Per Minute) + 并发上限
      → App Level → 按功能分配配额（生成 vs 检索）
        → Org Level → 总预算控制
          → Global Level → LLM Provider 限制兜底
```

**核心策略**:
1. **令牌桶限流**: 每用户分配 TPM 配额，Premium 用户更高
2. **并发槽控制**: 标准用户 2-4 并发，Premium 8+
3. **公平调度**: 混合短/长请求，避免饥饿
4. **优雅降级**: 限流时回退到更小模型或缓存响应
5. **语义缓存**: Redis + 向量搜索，相似查询命中缓存，节省 30-50% API 调用

from collections import defaultdict

class TokenBucketLimiter:
    """Per-user token bucket rate limiter"""
    def __init__(self, tpm_limit: int = 100000, max_concurrent: int = 3):
        self.tpm_limit = tpm_limit
        self.max_concurrent = max_concurrent
        self.semaphores: dict[int, asyncio.Semaphore] = defaultdict(

### 4.2 方案二：Go + Python 混合架构（推荐长期方案）

**适用场景**: 支撑千人+并发，长期运营的 SaaS 产品

#### 核心思路

**不是全部重写 Go，而是用 Go 重写性能关键路径，Python 保留 AI 逻辑层。**

这是 2026 年业界的共识模式：
- API Gateway / WebSocket 管理 → **Go**（万级连接管理）
- 任务队列 / 调度 → **Go Asynq**（高吞吐调度）
- LLM API 调用代理 → **Go Bifrost 模式**（40-50x 性能提升）

**阶段 2: Go LLM Gateway（第 3-5 周）**

```go
// internal/llmgateway/gateway.go
package llmgateway

type LLMGateway struct {
    clients    map[string]*http.Client  // 按 provider 维护连接池
    limiter    *RateLimiter             // 全局 + 每用户限流
    router     *ModelRouter             // 模型路由（主模型/备用模型）
    metrics    *prometheus.Registry     // Prometheus 指标
}

// StreamGenerate 高性能流式生成
func (g *LLMGateway) StreamGenerate(ctx context.Context, req *GenerateRequest) (<-chan StreamChunk, error) {
    // 1. 限流检查
    if err := g.limiter.Allow(req.UserID, req.EstimatedTokens); err != nil {
        return nil, ErrRateLimited
    }

    // 2. 模型路由（支持 fallback）
    provider := g.router.Route(req.Model)

    // 3. 流式调用 + 自动重试
    ch := make(chan StreamChunk, 64)
    go func() {
        defer close(ch)
        g.streamWithRetry(ctx, provider, req, ch)
    }()

    return ch, nil
}
```

#### Go + Python 通信方式

| 场景 | 通信方式 | 理由 |
|------|---------|------|
| API Gateway → FastAPI | HTTP 反向代理 | 简单直接，无需改造 |
| Task Dispatcher → AI Worker | gRPC | 高性能，支持流式 |
| AI Worker → WebSocket Hub | Redis Pub/Sub | 异步解耦，广播能力 |
| LLM Gateway → Provider | HTTP/2 长连接 | 连接池复用 |

#### 推荐 Go 技术栈

| 组件 | 推荐 | 理由 |
|------|------|------|
| Web 框架 | Fiber v3 / Gin | 高性能，生态成熟 |
| WebSocket | Fiber WebSocket / Gorilla | 百万连接实战验证 |
| 任务队列 | Asynq | Redis 生态复用，监控内置 |
| gRPC | google.golang.org/grpc | 标准选择 |
| LLM SDK | Eino / OpenAI Go SDK | Eino 更完整 |
| 监控 | Prometheus + Grafana | 行业标准 |
| 配置 | Viper | Go 配置管理标准 |
| 日志 | Zap | 高性能结构化日志 |

#### 成本与性能预期

| 指标 | 数值 |
|------|------|
| 开发时间 | 2-3 个月（Go 模块）+ 1 个月（集成调试） |
| 月度基础设施 | ~$350 (Go Gateway x2 + Python Worker x5 + Redis + MySQL) |
| 吞吐量 | 50-100 章节/分钟 |
| WebSocket 连接 | 10,000+ 并发 |
| 支撑并发 | 1000+ 人在线，200+ 人同时生成 |
| 百人排队时间 | 1-2 分钟 |

> **注意**: 吞吐量的真正瓶颈在 LLM API 而非应用层。即使 Go Gateway 能处理 500 章节/分钟，如果 LLM Provider TPM 限制为 100 万 tokens，实际吞吐也受限于此。Go 的价值在于**更高效地管理等待和调度**，而非加速 LLM 推理本身。

### 4.3 方案三：全 Go 重写（不推荐）

**为什么不推荐全 Go 重写**:

| 风险 | 说明 |
|------|------|
| **AI 生态断层** | Python 的 LangChain/LlamaIndex/HuggingFace 生态无法在 Go 中完整替代 |
| **代码量巨大** | 54 个 service，17K 行 Python 代码，重写至少翻倍工时 |
| **Agent 系统复杂** | 三省六部 7 个 Agent + 消息总线 + 权限矩阵，用 Go 重写代码量 3-4 倍 |
| **市场窗口** | 全重写 6+ 个月，竞品可能已经占领市场 |
| **团队学习成本** | 如团队无 Go 经验，生产力降低 50%+ 至少 3 个月 |
| **Eino 框架仍年轻** | 虽然字节在用，但社区生态、文档、第三方集成远不如 Python |

**唯一适合全 Go 的场景**: 团队有资深 Go 工程师 + 不急于上线 + AI 逻辑简单（仅 LLM API 调用，无复杂 Agent）。

### 5.1 最重要案例：Lovable（2025 年 2 月）

| 迁移耗时 | - | 约 2 个月 | 消耗 80% 研发资源 |

**Lovable 迁移的核心动因**: 单次用户请求需要 **50+ 并发 HTTP 调用**，Python 并发模型在这个场景下严重受限。这与 Arboris-Novel 的场景不同——我们的瓶颈是 LLM API 的 5-30 秒延迟，而非大量并发 HTTP 调用。

## 六、向量数据库升级方案

当前 libsql 单文件方案在多用户场景下无法满足需求，需升级：

| 方案 | 适用规模 | 优势 | 劣势 |
|------|---------|------|------|
| **pgvector (PostgreSQL 扩展)** | 中等（百万级向量） | 2026 年 95% 场景够用，运维简单，与业务库统一 | 超大规模性能下降 |
| **Qdrant** | 大（亿级向量） | 高性能，Go/Python SDK 完善，已在项目中用于 Mem0 | 需独立运维 |
| **Milvus** | 超大（十亿级） | 分布式架构，极致性能 | 运维复杂，资源消耗大 |

**推荐**: **Qdrant**（项目已有集成经验）或 **pgvector**（如切换到 PostgreSQL 统一数据层）。

## 十、核心结论

1. **不要全部换 Go** — 混合架构是 2026 年 AI SaaS 的业界共识。Python 负责 AI 逻辑（不可替代），Go 负责基础设施（性能优势明显）。

2. **先 Python 优化快速上线** — Celery + Redis + 水平扩展可在 1 个月内支撑 200-500 并发，验证商业模式。

3. **再 Go 渐进替换关键路径** — API Gateway、LLM Gateway、Task Dispatcher 三个模块用 Go 重写，获得 40-50x 性能提升。

4. **真正的瓶颈是 LLM API** — 无论用什么语言，千人同时生成的瓶颈在 LLM Provider 的 TPM 限制。Go 的价值在于更高效地管理排队和调度，以及用更少的服务器资源服务更多用户。

5. **字节跳动 Eino 是 Go AI 生态的最佳选择** — 生产级验证，与 Arboris 的 Agent 编排需求契合。
