# 批量章纲生成进度改造计划

## 目标

批量生成后续章纲属于分钟级任务。当前页面只保留一个“生成中”布尔状态，用户无法判断任务是否仍在运行、完成了多少、当前处理什么，以及失败后如何恢复。

本次改造将其升级为可恢复的后台任务，并明确区分：

- **全书进度**：已经完成正文的章节数 / 当前章纲总数。
- **本次任务进度**：本次已经生成并落库的章纲数 / 请求生成数。

## UI 方案

### 1. 配置弹窗

保留现有数量、预计总章节数和附加剧情提示。点击“生成”后立即关闭弹窗，并提示任务已转入后台。

### 2. 常驻任务卡

任务运行期间固定显示在章节轨底部：

- 本次进度：例如 `12 / 25 章`
- 当前范围：例如 `正在生成第 17～26 章`
- 当前阶段：准备上下文、生成章纲、保存结果
- 预计剩余时间：首批完成后按实际耗时滚动估算
- 真实进度条：只使用已经落库或明确失败的章节数计算

任务结束后保留结果摘要，用户确认后可关闭。

### 3. 任务详情

详情弹窗逐章展示四种状态：

- 等待生成
- 正在生成
- 已完成
- 生成失败

失败章节不终止后续批次，任务结束后提供“重试失败章节”。

### 4. 中止语义

“停止后续批次”不会强行打断已经发给模型的请求；当前批次完成后停止尚未开始的章节，避免产生半份 JSON 或不确定落库状态。

## 开发方案

### 后端

1. 新增 `outline_generation_tasks` 持久化任务表。
2. 新增创建、查询当前任务、查询详情、停止、重试接口。
3. 后台按最多 10 章一个批次调用现有章纲生成能力，每批单独落库和更新进度。
4. 任务状态写入数据库，使任意应用副本都能查询，并支持刷新页面后恢复。
5. 单批异常记录失败章号后继续执行；全部结束后标记为完成、部分完成、失败或已停止。

### 前端

1. 增加任务 API 类型和轮询逻辑。
2. 写作台启动任务后不阻塞页面，每 2 秒读取一次任务状态。
3. 检测到完成数变化时刷新项目，使新章纲渐进出现在章节列表中。
4. 增加常驻任务卡和逐章详情弹窗。
5. 页面重新进入时自动恢复当前未结束任务。

## 验收标准

- 点击生成后 1 秒内看到后台任务卡。
- 页面始终能看到真实完成数、当前批次范围和任务阶段。
- 刷新页面后任务状态可恢复，任务继续在服务器执行。
- 已完成批次的章纲会逐步出现在章节目录中。
- 单批失败不会丢失前面已完成结果，也不会阻止后续批次。
- 用户可以停止尚未开始的批次，并可重试失败章节。
