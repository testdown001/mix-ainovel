# 第四阶段：可恢复创作任务与任务中心

## 背景

长篇正文、批量章纲和蓝图生成都属于分钟级任务。原有调度器虽然支持 Redis 状态和自动重试，但页面刷新后作者只能重新进入当前页面，无法快速判断任务是否仍在运行；批量任务失败时也缺少“只续跑失败章节”的入口。服务重启还可能让 `running` 任务停留在假状态。

本阶段借鉴 Hermes Agent 的持久会话、检查点和可恢复执行思路，继续复用现有 Go Dispatcher + Redis + Python Worker，不新增平行任务系统。

## 交付内容

### 1. 逐章检查点

- Worker 在批量生成每章完成后上报 `checkpoint`。
- 检查点包含最后处理章节、成功章节、失败章节和批次总数。
- 网关将检查点与任务状态一起保存，前端可在断线/刷新后恢复展示。
- 已完成章节依靠数据库中的选中版本幂等复用，不因任务重启重复扣费或重写。

### 2. 失败章节续跑

- 新增 `POST /tasks/{task_id}/retry`。
- 批量任务从结果中的失败章节构造子任务，只提交失败章节。
- 任务在结果汇总前中断时，沿用原始章节列表，Worker 自动跳过已经交付的章节。
- 子任务通过 `parent_task_id` 与原任务关联，原任务只读保留，便于追溯。

### 3. 服务重启恢复

- 网关启动时扫描 Redis 中仍为 `pending/queued/running/retrying` 的任务。
- 清理队列中的旧副本并重新入队，状态改为 `recovered`。
- 任务保留最近检查点，恢复后沿用现有章节幂等策略。
- 任务和用户任务集合保留 7 天，给作者留下足够的回看与续跑窗口。

### 4. 写作台任务中心

- 写作台增加右下角可折叠“本书任务”面板。
- 展示进行中、部分完成、失败和近期完成任务的阶段、进度、检查点和失败章节。
- 支持刷新同步和“仅续跑失败章节”，续跑成功后自动刷新当前作品。
- 任务列表接口增加项目归属和结果字段，并校验用户只能查看自己的任务。

## API 变化

- `POST /tasks/{task_id}/retry`
- `GET /tasks/{task_id}/status` 响应增加 `project_id`、`parent_task_id`、`checkpoint`
- `GET /tasks/user/{user_id}` 响应增加项目、结果和检查点，并启用归属校验
- Worker 进度回调新增可选 `checkpoint` 字段

## 验收标准

- 批量 5 章中 3 章成功、2 章失败时，任务显示“部分完成”，并能只续跑 2 章。
- 刷新写作台后，仍能看到当前小说的任务进度和最后处理章节。
- 网关重启后，未完成任务重新进入队列；已交付章节不重复生成。
- 非任务所有者不能读取、取消或续跑任务。
- Go、后端和前端回归测试通过，生产构建和健康检查通过。
