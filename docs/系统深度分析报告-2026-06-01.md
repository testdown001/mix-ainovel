## 一、执行摘要

**系统是什么。** Arboris-Novel 是一个 AI 辅助小说创作平台，技术栈为 FastAPI(Python 3.11) 后端 + Vue3(TypeScript) 前端 + 一个 Phase 2 引入的 Go Gateway 边缘层。核心工作流：概念对话 → 蓝图生成 → 章节大纲 → RAG 检索辅助的 AI 章节生成 → 多版本评审 → 向量化沉淀。后端实测约 **6.3 万行 Python**（`backend/app` = 63,184 行），前端 `frontend/src` 约 **3.56 万行**，全仓 **153 次提交**。

**整体健康度评级：隐患偏危险（C 级 / 黄偏红）。** 真实生成主干清晰、统一输出契约扎实、世界观数据多数确有读写闭环——内核是健康的。但它被一圈"建了不用、文档与代码互相矛盾、运行即崩"的腐坏外围包裹，且安全与测试两条护城河存在真实硬伤。

**最关键结论（一针见血）：**

1. **Go 生产入口当前源码无法编译（critical）。** `gateway/cmd/gateway/main.go` 有 4 类签名漂移（`middleware.CORSWithOrigins`/`cfg.CORS`/`taskdispatcher.Config.InternalCallbackSecret`/`NewHandler` 参数数不符），`go build ./cmd/gateway/` 实测 5 处报错。生产 Docker 构建会直接失败，当前能跑的只剩一个被提交进仓库、且本次还被修改（`M`）的 **约 32MB 陈旧二进制 `gateway/api`**（实测 32,748,744 字节）——而它编译自 `cmd/api`，根本不是默认运行的 `gateway`。源码与运行物不可对账。

2. **支付激活会员存在代码级必崩 bug，但当前因 payment 路由未注册而不可达（critical，潜伏，挂载即触发）。** `payment_service.py:137` 调 `upgrade_to_premium(order.user_id, expires_at, plan=plan)`，但 `quota_service.py:173` 的签名只有 `(user_id, expires_at=None)`，一旦该方法被执行必抛 `TypeError`。**但需诚实指出**：`payment` 路由从未在 `api_router` 注册（实测 23 个路由无任何 payment），因此"用户付款 → 激活会员"这条链路在默认部署下**根本走不到**——这是一个潜伏缺陷，不是线上已发生的资金损失。**修复必须成对进行**：挂载 payment 路由与修复 `plan=` 参数二者缺一不可，只挂路由不修参数会上线即崩，只修参数不挂路由则功能仍不存在（详见 4.4 与路线图）。

3. **明文 API 密钥写进 llm.log（high）。** `app/utils/llm_tool.py:80` 把 `dict(request.headers)` 整体打印，上游 `Authorization: Bearer sk-...` 明文落入 `llm.log`（20MB×10 滚动留存），`llm_service.py` 的 sha256 脱敏被底层完全绕过。

4. **大量"声称 vs 实现"的契约断裂。** ① RAG 的 Agentic 证据层（千行 `_enforce_evidence_budgets` + LLM 评分）算出来后**根本不进生成提示词**，仅用于归档/telemetry；② Agent 协作层里**shangshu/libu 从不被调用**、消息总线空转、bingbu 生成实为传统管线的薄壳；③ 文档反复称 `knowledge_retrieval_service` 已弃用，实则仍是 `two_stage` 模式的活依赖。

5. **质量护栏形同虚设。** CI 后端只跑 62 个测试文件中的 **1 个**（`tests/test_writer_quality_updates.py`），核心 `PipelineOrchestrator.generate_chapter` 与 2761 行的 `writer.py` 路由**无任何端到端覆盖**；前端**零测试框架**；还存在引用已删模块、`debug` 默认 `True` 致生产 HTTPS/HSTS 易静默关闭等问题。

**一句话定调：** 这不是一个"全是亮点"的系统，而是一个"健康内核 + 危险外围"的系统。内核能跑、契约正确；但生产 Go 入口编译不过、支付链路潜伏必崩且功能整体未上线、密钥明文落盘、测试近乎空转——这些任意一条都不该带进生产。

## 二、系统真实运行画像（设计文档声称 vs 代码实现）

### 2.1 一次章节生成的真实主路径

**默认配置**：前端 `preset=fast`、`useAgent=false`。是否走异步取决于前端 `detectAsyncMode` 探测 Go Gateway 的 `/tasks/stats` 是否可达。

```
默认同步路径（最常见，尤其在 docker-compose.yml 无网关的最小栈下）：
Browser
  └─> POST /api/writer/advanced/generate        (writer.py:320，SSE 直连)
        └─> HybridExecutor.generate_chapter(use_agent=False)   (hybrid_executor.py:50)
              └─> _use_legacy_pipeline                          (hybrid_executor.py:147)
                    └─> PipelineOrchestrator(session).generate_chapter   (pipeline_orchestrator.py:205)  ★唯一真实生成引擎
                          └─> PipelineConfigService.resolve_config → preset=fast 命中 enable_fast_path
                                └─> FastGenerationFlowService.run            (三向分流命中 fast)
                                      └─> SingleVersionGenerationService.generate  (单次 LLM)
                                            └─> 轻量人味化/可选 polish/实体别名替换
                                                  └─> GenerationFinalizeService (持久化)
                                                        └─> 后台 async_finalize：向量化 + 记忆更新 + 奏折归档
        归一化输出 -> normalize_generation_result (generation_contract.py:56)

生产异步路径（仅 docker-compose.prod.yml 拓扑生效）：
Browser -> Nginx -> Go Gateway(cmd/gateway) -> POST /tasks/submit
  -> Redis 优先级队列 -> WorkerPool.callWorker
  -> HTTP POST app:8000/api/internal/tasks/execute  (task_worker.py:178)
  -> HybridExecutor.generate_chapter  (★同一引擎，契约一致)
  -> 进度回调 -> Redis Pub/Sub -> WebSocket Hub(/ws) -> 前端
```

### 2.2 关键澄清：声称 vs 实现

| 维度 | 文档/记忆声称 | 代码实现真相 |
|---|---|---|
| **legacy vs agent 默认走哪条** | 两套对等生成引擎 | 默认走 **legacy（fast preset）**；Agent 模式需手动开启，且章节生成经 `generation_bridge.py:57` **回调同一个 `PipelineOrchestrator`**，并非独立引擎 |
| **先进多 Agent 协作** | 需求解析→上下文规划→调度→质量审核 | 主路径只调用 taizi/hubu/zhongshu/bingbu/menxia 的 `.process()`；**shangshu/libu 从不被调用**，`PERMISSION_MATRIX` 已删，消息总线 `_process_loop` 空转（`message_bus.py:88`） |
| **RAG 真实入口** | `chapter_context_service`（活）/`knowledge_retrieval_service`（弃用） | 主入口确为 `ChapterContextService.retrieve_multi_query`；但 KRS **未弃用**，仍被 `evidence_router_service.py:203` 在 `rag_mode=two_stage` 时实例化（默认关闭而已） |
| **Agentic 证据预算** | "四类预算 score 降序→数量限制→token 截断"为核心价值 | `_enforce_evidence_budgets` 只裁剪 `evidence_pack`，而提示词消费的是**预算前**的 `resolved_prefetch.rag_context`；预算/评分结果**不进提示词**，仅 telemetry |
| **Go Gateway 是否在链路中** | "Nginx→Go Gateway→FastAPI"是生产主链路 | **默认 `docker-compose.yml` 无网关**，是 Browser→FastAPI 直连；只有 `docker-compose.prod.yml` 才引流到 Gateway，且 Gateway 源码当前编译不过 |
| **支付/会员功能** | 平台具备付费会员能力 | **FastAPI 侧支付功能整体未接线**：payment 路由从未在 `api_router` 注册，付费/会员能力在默认部署下不存在（详见 4.4） |
| **后端代码规模** | `SYSTEM_ANALYSIS_REPORT.md` 称 230 万行 | 实测 6.3 万行（把 `.venv` 算进去了，虚高 ~36 倍） |

## 三、分子系统逐项评估

### 3.1 整体架构与分层纪律 — 健康度：危险

- **亮点**：`main.py` 入口清晰，lifespan 做 DB init + 提示词预热 + reranker 检查；中间件按正确顺序叠加（RequestId 最外层）。`core/config.py` 用 pydantic-settings 集中配置。基础设施链路（auth/config/usage/prompt/llm）确实贯穿 Repository 层，`core/dependencies.py` 的 DI 是标准模式。健康检查双挂、含 DB 探活。
- **关键问题**：
  - 分层名实不符：Repository 层近乎装饰品，业务大面积裸 ORM（13/15 业务 Router 直连 `select()`）；Service 层 117 文件碎片化。
  - 死代码：`core/error_handler.py`（约 333 行完整实现，全库 0 入站引用、`main.py` 未注册任何 `add_exception_handler`，confirmed/low）；`agents/simplified/`（空目录，confirmed/low）。
- **建议**：明确分层契约——要么坐实 Repository 层，要么承认"Router 直连 ORM"为既定风格并删除半成品 Repository；接入或删除 `error_handler.py`。

### 3.2 章节生成管线（系统核心） — 健康度：隐患（健康内核 + 冗余外围）

- **亮点**：真实生成引擎**单一收敛**到 `PipelineOrchestrator` + `SingleVersionGenerationService`，避免了最危险的"多套真生成实现"；统一契约 `normalize_generation_result` 有 `test_generation_contract.py` / `test_hybrid_executor_contract.py` 双覆盖；13 个 `generation_*` 阶段服务是高质量拆分（**非重复实现**），全部装配并调用。
- **关键问题**：
  - 旧 Celery 路径腐坏（`chapter_tasks.py:165`）：构造器与 `generate_chapter` 双重签名不匹配，运行必抛 TypeError。**注意**：核查纠正了原断言——这**不是无引用死代码**，`/async/generate`(`writer.py:274`) 是已注册可达的 live 端点 + 生产 Celery worker 在跑（partial/medium），任何直接命中即入队崩溃任务。
  - 2 个死 agent：`shangshu_agent.py`、`libu_agent.py` 在主路径从不 `.process()`（confirmed/low）。
  - `PipelineConfig` 开关已膨胀到 **38–44 个**（口径：静态声明约 38，含运行时注入约 44，见 4.3 脚注），`resolve_config` 中同一开关可被 4 处先后覆写（preset 硬编码 → `writer_fast_mode` → `writer_ultra_fast_mode` → `flow_config`），生效值难以静态推断（low）。
- **建议**：删除 `/async/generate` + `chapter_tasks.py` 的 Celery 任务（异步已由 Go 网关承担）；删除/下沉 shangshu/libu；把 preset 解析改为声明式配置表。

### 3.3 Agent 系统（自创先进多 Agent 架构） — 健康度：隐患（协作已成门面）

- **关键问题**（均 confirmed）：
  - 消息总线门面：`PERMISSION_MATRIX` 已删、`_can_send_to` 恒返回 True、`_process_loop` 空转；shangshu/libu 注册但永不调度，`next_agent` 字段**无任何消费者**（medium）。
  - 生成智能体薄壳：`bingbu_agent.py:182` → `AgentGenerationBridge` → `PipelineOrchestrator`，正文/RAG/多版本全部复用传统管线（与文档"对等第二引擎"不符）。
  - `generation_bridge.py` 内 3 个死类（`AgentConsistencyChecker`/`AgentReviewAdapter`/`AgentForeshadowingIntegrator`）重复了 `tools/` 下的活实现，且含空桩 placeholder（low）。
  - **前端假象**：`AgentFlowVisualizer.vue` 硬编码把"协调智能体/一致性智能体"置为 completed，但后端从不发这些阶段事件。
- **建议**：删除死 agent、死类与消息总线（或明确收敛为顺序调用）；前后端统一 Agent 事件契约。

### 3.4 RAG / Agentic RAG — 健康度：隐患（契约断裂）

- **亮点**：基础多查询向量 RAG 链路健壮（批量 embedding、并行检索、按 chunk_id 去重保最高分、min_score 过滤、可选 rerank，全量日志）；双层叙事摘要触发链完整闭合（卷→书→时间线，均带增量 hash 去重）；BM25 是功能完整的 MySQL 实现，非空壳。
- **关键问题**：
  - **证据预算/评分对提示词无效（high）**：`_enforce_evidence_budgets`(`evidence_router_service.py:385`) 只裁剪 `evidence_pack`，而 `pipeline_orchestrator.py:559` 取的是预算前的 `resolved_prefetch.rag_context`；`evidence_pack` 唯一出口是 `graded_summary` 归档。LLM 评分（`evidence_grader_service.py:96`）只打 `graded_out` 标记、不删除、无消费方。
  - **`ProjectMemory.global_summary` 多写方语义冲突（medium）**：该字段被两个写入方写入——`FinalizeService`(`finalize_service.py:211`) 写"按章滚动前文摘要"，`BookSummaryService`(`book_summary_service.py:96`) 写"全书卷级聚合摘要"，后者经 `chapter_post_processor.py:263` 间接触发；二者写同一字段，语义冲突。下游 KRS/ConsistencyService 期望前文语义，被书级摘要覆盖后错乱。
  - `local_plot` 证据 score 恒为 0.0（传入已格式化字符串，medium）；hybrid 切换后 BM25 无历史回填（medium）。
  - 向量库未启用/初始化失败时存在降级路径，但分支分散、日志级别不一致（low）。
- **建议**：让 `build_prompt_stage` 消费预算后的 `evidence_result`，否则把 Agentic 证据层明确降级为诊断模块；为 `global_summary` 拆分独立字段（书级摘要写独立列），消除并发写冲突。

### 3.5 数据模型与数据库 — 健康度：隐患

- **亮点**：双后端经 `sqlalchemy_database_uri` 统一抽象、全异步；`_MetadataAccessor` 描述符巧妙规避保留属性冲突；提示词用 SHA256 幂等同步避免覆盖用户手改；关键唯一约束齐全。
- **关键问题**（均 confirmed）：
  - 7 张表未在 `models/__init__.py` 注册，建表依赖导入副作用——其中 **`payment_orders` 表连主程序正常路径都建不出来**，因为 payment 路由从未被 include（high，详见 4.4）。
  - 无 Alembic，靠硬编码错误字符串匹配的"启动期补列"，只能 ADD COLUMN、字符串拼接 DDL、SQLite/PG 直接 return（low，机制脆弱但安全风险被高估）。
  - SQLite 未开 `PRAGMA foreign_keys=ON`，所有 CASCADE 在 SQLite 下失效，删项目留孤儿行（medium，仅影响开发后端）。
  - **`ForeshadowingAnalysis` 查询恒失败（high，活跃接口）**：模型主键为自增 `id`（`foreshadowing.py:150`），`project_id` 是 `unique=True` 普通列（`:151`）；但 `foreshadowing_service.py:389` 用 `session.get(ForeshadowingAnalysis, project_id)` 按主键取行，恒返回 None → 每次新建 → `project_id` unique 约束第二次必冲突。该查询由活跃路由端点 `foreshadowing.py:547` 调用，因此**对同一项目第二次调用伏笔分析接口必崩**。
  - `CharacterState.character_id` NOT NULL 但写入路径会传 None/写 0 伪记录（medium）。
  - **热点查询缺复合索引（medium）**：`(project_id, chapter_number)` 等高频联合过滤只有单列索引，是真实性能债。
  - `CausalChain`/`StoryTimeTracker.chapter_time_map` 只读不写（写入方法 `add_causal_chain`/`update_chapter_time` 零调用），读取恒空（medium，确认为孤岛）。
- **建议**：补全 `__init__.py` 注册与 payment 路由挂载；引入 Alembic；SQLite 注册 connect 事件开 FK；修 `ForeshadowingAnalysis` 查询（改 `select().where(project_id==...)`）；为热点表补 `(project_id, chapter_number)` 复合索引。

### 3.6 前端（Vue3 + TS + Naive UI + Pinia） — 健康度：隐患

- **亮点（纠正过时记忆）**：`MiddleProductViewer`/`DiagnosticPanel`/`AgentFlowVisualizer` **三个曾被记为"空壳"的组件均已接真实数据**，应更新 CLAUDE.md/MEMORY.md。`vue-tsc --build` 全量通过；SSE 的 9 个 `middle_product` type 分支与后端 `emit_*` 严格一一对应；路由守卫完整；Tailwind v4 用法正确；WS 有指数退避重连+优雅降级。
- **关键问题**：
  - 异步(Go Gateway)路径**完全丢失中间产物**（medium）：`TaskProgressEvent` 只含 progress/stage/message，`task_worker.py` 不转发 `middle_product`，导致异步模式下 9 个 Tab 全部"暂无数据"。
  - Agent 流程可视化 stage→节点映射与后端实际事件不对齐（medium）。
  - ~10 个死组件文件（脚手架 `HelloWorld`/`TheWelcome`/`WelcomeItem` + 重构残留 `ChapterWorkspace*`/`CharactersEditor`/`LLMSettings`/`BlueprintCard`/`EmotionBeatSelector`/`TypewriterEffect`，约 1442 行，均 confirmed/low）。
- **建议**：异步路径透传或事后拉取中间产物；删除死组件；中间产物 ref 补类型标注。

### 3.7 Go Gateway（Phase 2） — 健康度：危险

- **亮点**：`TaskDispatcher` 的 Redis 优先级队列、用户级并发 CAS、指数退避重试、Pub/Sub 进度扇出**设计完整自洽**，与 `task_worker.py` 的 `/execute` 契约精确对齐，是真正闭环的部分；前端"探测可用即用、不可用回退 FastAPI"的降级设计优雅；`runtime_topology.md` 边界规则写得清楚。
- **关键问题**：
  - **`cmd/gateway` 源码无法编译（critical）**，生产入口构建即失败（详见执行摘要）。
  - **约 32MB `gateway/api` 二进制被提交进仓库且本次被改动（medium）**，实为 `cmd/api` 产物，与默认运行的 gateway 不一致，源码-二进制不可对账。
  - **反向代理未透传已校验身份（medium）**：Go 网关未将已校验用户身份传给下游 FastAPI，导致 FastAPI 仍需独立鉴权（双重鉴权），网关边缘校验对业务实际无强约束效力。
